破格长文栏 · Breakout Column（L-06）

正文是一条居中窄栏（默认 65ch），段落左边界全部对齐到它；而引用块、图、表格突破栏宽伸进更宽的破格层，还有一条全出血色带铺满视口。靠宽度差制造阅读节奏：窄栏是常态，宽块是重音，页边注是耳语。

滚动通读一遍，注意右页边那条小注；再把窗口缩窄到手机宽度，看破格块如何收回、页边注如何降级成内联注。左下角实时读数会告诉你当前有没有横向溢出。

行宽是排版的隐形地基

行宽（measure）指的是一行文字从左边到右边的长度，通常用字符数 ch 衡量。它不写在任何一个显眼的属性里，却决定了整篇文章读起来是顺流还是逆流——眼睛在行尾折返行首时，要重新定位下一行的起点，这段"回扫"的距离随行宽线性增长。

短行（35–45ch）回扫成本低，适合快速扫读与移动端；中长行（55–70ch）是长文阅读的舒适区，也是本页正文栏的默认取值；一旦越过 75ch，回扫定位开始出错，读者会不自觉地重读同一行，或者跳到下面两行去。这不是审美偏好，是眼球运动的物理约束。

所以破格栏这个布局的核心并不是"让图变宽"这么简单。它先在页面上确立一条稳定的可读基准——也就是正文栏——再把少数元素放出这条基准之外。基准一旦动摇，破格就失去了参照物，页面上只剩下一堆宽度不同的块，读者每翻一段都要重新寻找左边界。

页边注就是"基准之外"的最小单位：它挂在段落右侧的页边，不打断正文的行流。宽屏时飘在栏外，窄屏时必须降级成内联注——这个响应式分支是这类布局最常漏掉的一处。

实现上，本文用的是 CSS Grid 的五条命名线：full、breakout、content 三档宽度共用同一套轨道。正文写 grid-column: content，破格块写 grid-column: breakout，全出血色带写 grid-column: full。两侧各留一条对称的溢出轨道，宽度由浏览器算成 (BREAKOUT − 正文宽) / 2，所以无论参数怎么调，破格块左右溢出的量永远相等。

「读者不该意识到自己在读一行字。行宽合适的时候，文字是透明的；行宽一旦失衡，读者就开始看见排版本身。」 — 关于可读性的一句老话

两套宽度，不是一套宽度加个例外

很多人把破格理解成"正文容器加一个负 margin 的例外"，这是误解。破格栏天生有两套并存的宽度：正文栏定义可读节奏，破格层定义视觉重音。它们不是主次关系，而是两个平等的层级——正因为平等，破格块才能反过来嵌套：页边注那一段就是外层跨 content-start → breakout-end、内层再切两列的嵌套网格，段落落在内层第一列后，左边界与全篇正文严丝合缝。

上面这张表格也是破格块。它内部自带 overflow-x: auto——注意这是"块内可横滚"，和"整页出现横向滚动条"是两件完全不同的事。前者是正解，把可能的溢出关在一个小盒子里；后者是布局已经坏了的症状，必须从宽度源头修。

全出血层比破格层更宽：它直接铺到视口左右边缘，连页面 padding 都不吃。长文用它来切分"幕"——读者滚过一条深色带，就知道上一章结束了。

FULL-BLEED · 章节分隔

溢出必须从源头掐掉

这类布局最流行的假解法是给 body 加一句 overflow-x: hidden：横向滚动条确实没了，看起来问题解决了。但元素的实际宽度一点没变，它只是被裁掉了——打印会截断、Ctrl+F 定位会滚到看不见的地方、用户缩放页面后立刻复现。更糟的是它给整页建了一个滚动容器，页面里所有 position: sticky 会当场失灵。

正解是让宽度从一开始就不可能超：破格轨道的上限用 minmax(0, …) 夹住，正文轨道用 min(MEASURE × 1ch, 100% − 2 × padding) 兜底，破格块自己再加一句 max-width: 100%。三处约束叠加之后，无论视口多窄、参数多大，横向溢出都不会发生——左下角的读数就是这条的实时证据。想看看反例长什么样，勾上顶部那个"作死试验"。

最后回到行宽本身：MEASURE 的上限卡在 90ch 只是"还能读"，真正的舒适区是 55–70ch。因为回扫成本随行宽上升，越过约 75 个字符后阅读速度会明显掉下来——这条约束不该被"排版看起来更饱满"的审美需求冲掉。
